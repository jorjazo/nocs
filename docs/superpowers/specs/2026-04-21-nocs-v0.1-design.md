# NOCS v0.1 — Design Spec

**Date:** 2026-04-21
**Status:** Draft, pending user review

## 1. Product framing

### Target users

- **v0.1 (now):** A solo amateur astrophotographer operating on the local network. Typical setup: one mount, one main cooled camera, one filter wheel, one focuser. Client is a laptop or a phone on the same LAN as the NOCS server.
- **End game (future, persona B):** Remote-hosted and/or shared observatories with multiple authenticated users, accessed over the public internet.

Every design decision below is evaluated against v0.1 needs while preserving a non-hostile path to persona B.

### Why NOCS vs. INDI + Ekos + KStars

The user experience is the differentiator: a single web-based UI, one install, no KStars/Ekos/INDI panels to configure. Under the hood, NOCS reuses INDI as a driver backplane so it inherits the driver ecosystem from day one rather than reimplementing dozens of vendor protocols.

### Goals (v0.1)

1. Take a real imaging session end-to-end: connect hardware, slew to a named target, plate-solve and sync, autofocus, run an N × exposure × filter sequence with dithering.
2. Never require the user to look at an INDI config panel, a CLI, or KStars.
3. Run on Linux x86_64 and Raspberry Pi 4/5 (arm64). Development and CI run on simulators only.

### Non-goals (v0.1)

Explicitly out of scope. All are valid v0.2+ candidates; the architecture must not preclude them.

- Autoguiding (native or PHD2).
- Multi-target scheduler.
- Calibration-frame workflows (darks, flats, bias).
- Automated meridian flip.
- Rotator / dew-heater / roof control.
- Full sky chart / planetarium UI.
- Multi-user accounts, RBAC, remote internet access, controller-role semantics (all deferred to persona B).
- Advanced observability (Prometheus/OpenTelemetry).

### Success criteria for v0.1

The system is considered shipped when a user can:

1. Install via a single `.deb` (or Windows installer) on a fresh machine with no JRE preinstalled.
2. Connect a supported mount, camera, filter wheel, and focuser through the web UI without editing config files.
3. Type `M31` into a target search, click Slew, have NOCS plate-solve and sync the mount automatically.
4. Run an autofocus routine, then run a sequence of N subs per filter with between-sub dithering.
5. Trigger a configured safety rule (for testing, e.g. a simulated "rain" sensor event) and observe the mount park and the sequence abort.
6. Press E-stop and observe the mount park, exposure abort, and cooling ramp halt.

## 2. Comparison with INDI/Ekos

| Concern | Ekos + INDI + KStars | NOCS v0.1 |
|---|---|---|
| User-facing surface | Three applications, stacked panels, driver tab per device | One web UI |
| Driver ecosystem | INDI (hundreds of drivers) | INDI, via NOCS backplane (user sees none of it) |
| Remote access | Possible via X forwarding / VNC / webapps on top | Native: HTTP server, browser client |
| Config persistence | INDI `.xml` profiles, Ekos profiles, KStars settings | One SQLite DB + a `config/` dir |
| Multi-client | Limited | First-class, LAN-style free-for-all in v0.1; controller-role in persona B |
| Scripting | KStars DBus / INDI properties | HTTP REST API from day one |

## 3. Personas & trajectory

### v0.1 — solo LAN imager

- Single server on the observatory machine (laptop or RPi).
- One token in `config.yaml` shared by the user's own devices (laptop + phone).
- Mount keeps tracking and sequences keep running if the client disconnects (see §6, safety).
- No accounts, no TLS required (LAN), no WAN exposure.

### Persona B — remote-hosted multi-user (future, not v0.1)

When persona B work begins, the following additive changes are anticipated:

- Migrate auth from static token to user accounts + per-user tokens (SQLite-backed).
- Introduce a `controller` role: one client holds the write lock for commands at a time; others are read-only observers. Any authenticated client can trigger E-stop.
- Introduce a lease/heartbeat so an abandoned "controller" session is reclaimable.
- TLS termination at a reverse proxy; NOCS still speaks HTTP internally.
- Optional Postgres backend in place of SQLite.
- Per-user session quotas, audit logs, possibly billing hooks.

None of these require schema changes that invalidate v0.1 data; the REST API surface stays the same, with new endpoints added rather than old ones removed.

## 4. System architecture

### 4.1 Layered view

```
  ┌──────────────────────────────────────────────────────────┐
  │               Web client (React + Vite + TS)             │
  └──────────────────────────────────────────────────────────┘
                  ▲ REST  ▲ SSE  ▲ HTTP (FITS / thumbs)
                  │       │       │
  ┌──────────────────────────────────────────────────────────┐
  │  HTTP layer — Spring Boot 3, virtual threads              │
  │  REST controllers · SSE controllers · static file server │
  └──────────────────────────────────────────────────────────┘
                                │
  ┌──────────────────────────────────────────────────────────┐
  │                      Service layer                       │
  │  Configuration · Location · Device · Imaging · Target    │
  │  PlateSolving · Safety · Session · ImageStore            │
  └──────────────────────────────────────────────────────────┘
                                │
  ┌───────────────────┐  ┌───────────────────────────────────┐
  │  Event bus        │  │  Persistence                      │
  │  Project Reactor  │  │  SQLite (Flyway) + FITS on disk   │
  │  (in-process)     │  │                                   │
  └───────────────────┘  └───────────────────────────────────┘
                                │
  ┌──────────────────────────────────────────────────────────┐
  │              Abstract device layer                       │
  │  Mount · Camera · FilterWheel · Focuser (state machines) │
  └──────────────────────────────────────────────────────────┘
                                │
  ┌──────────────────────────────────────────────────────────┐
  │             Hardware layer (driver adapters)             │
  │  INDI client adapter (v0.1 default; hidden from user)    │
  │  · future: native Java drivers · Alpaca adapters         │
  └──────────────────────────────────────────────────────────┘
                                │
  ┌──────────────────────────────────────────────────────────┐
  │  Supervised child process: indiserver + vendor drivers   │
  └──────────────────────────────────────────────────────────┘
```

### 4.2 Process model

One NOCS Java process. It launches and supervises an `indiserver` child process with the configured driver set. Users never interact with `indiserver` directly; its lifecycle, logs, and crashes are owned by NOCS.

### 4.3 Concurrency model

- JDK 25 with virtual threads. HTTP handlers are virtual-thread-backed; blocking I/O to the INDI client, ASTAP, and disk is fine.
- The event bus is Project Reactor. Services expose `Flux<Event>` streams internally; the SSE layer adapts these to HTTP streams.

## 5. Interop strategy (driver backplane)

### 5.1 Decision

NOCS v0.1 uses **INDI as the driver backplane**. NOCS launches `indiserver`, speaks the INDI XML protocol over TCP to it, and exposes its own NOCS abstractions to clients. The end user never sees INDI concepts.

### 5.2 Rationale

- Collapses v0.1 scope from "reimplement every vendor protocol" to "design good abstractions + consume a proven driver stack."
- INDI already covers the target device classes (mounts, cameras, filter wheels, focusers) with mature drivers.
- The "no KStars/Ekos" promise is preserved: INDI is infrastructure, not UX.

### 5.3 Extension points (architectural, not v0.1 features)

The abstract device layer is the ground truth. v0.1 ships one adapter (INDI). The architecture explicitly allows future adapters:

- Native Java drivers for specific devices where the INDI driver is lacking.
- ASCOM Alpaca adapter for persona B, especially for Windows-backed remote rigs.

Adapters plug into the same abstract device interfaces; services never know which adapter is in use.

### 5.4 INDI client scope for v0.1

- Pure Java INDI client (XML over TCP). No JNI, no bundled C libs in the NOCS process itself.
- Supports: enumerate properties, set switch/number/text properties, subscribe to property updates, transfer BLOBs (FITS images).
- NOCS supervises `indiserver` lifecycle: start, stop, restart on crash with backoff, propagate logs.

## 6. Safety model

Safety is first-class. The SafetyService owns an in-process rule engine that subscribes to events and issues commands.

### 6.1 Weather / environmental interlocks

**Configurable rule engine, YAML-defined.** v0.1 supports a fixed vocabulary (not a general DSL):

**Rule conditions:**
- `humidity_above: <percent>`
- `rain_detected: true`
- `altitude_below: <degrees>` (target altitude, not sun)
- `sensor_offline: <sensor_name>` (e.g., weather sensor gone silent for N seconds)

**Rule actions:**
- `pause_sequence` — suspend current sequence, mount keeps tracking
- `abort_and_park` — abort in-flight exposure, stop sequence, park mount
- `e_stop` — everything stops (see §6.3)

**Example `safety.yaml`:**

```yaml
rules:
  - name: humidity-high
    when: { humidity_above: 90 }
    then: pause_sequence
  - name: rain
    when: { rain_detected: true }
    then: e_stop
  - name: low-altitude
    when: { altitude_below: 20 }
    then: abort_and_park
```

Rules evaluate on every relevant event; triggering is idempotent (a rule that fires while already-triggered is a no-op).

### 6.2 Client disconnect / watchdog

**v0.1 policy: no watchdog.** Mount keeps tracking; sequences keep running; event stream to the disconnected client is dropped. Cooperative free-for-all auth (§7) means the "same user" may reconnect from another device and resume.

This is explicitly a persona-A choice. **Persona B flag:** when multi-user arrives, a lease+heartbeat must be introduced on the controller role (the API surface for this is reserved, see §7.3).

### 6.3 E-stop

Always available. Any authenticated client can invoke `POST /api/safety/e-stop`. Effects in v0.1:

1. Abort in-progress exposure on the camera. Any partial download that completes is saved with `e_stopped: true` in the FITS header; a failed download is discarded.
2. Stop the current sequence; mark it `aborted`.
3. Park the mount.
4. Halt camera cooling ramp (hold current setpoint, do not warm up automatically — warming is a manual decision).
5. Emit a high-priority event on the bus; all clients see an E-stop banner.

E-stop is logged with caller identity and reason (if provided) in the session history.

### 6.4 State machines on abstract devices

Safety rules can only reason correctly if device state is explicit. v0.1 defines:

**Mount**
```
disconnected → idle → slewing → tracking → parking → parked
                 ↕
               error
                 ↕
             e_stopped
```

**Camera**
```
disconnected → idle → cooling → ready → exposing → downloading → idle
                                     ↕
                                   error
                                     ↕
                                 e_stopped
```

**FilterWheel**
```
disconnected → idle → moving → idle
                 ↕
               error
```

**Focuser**
```
disconnected → idle → moving → idle
                 ↕
               error
```

All transitions emit typed events on the bus. The SafetyService and SessionService subscribe.

## 7. Authentication & multi-client semantics

### 7.1 Auth (v0.1)

**Static token** stored in `config.yaml`. Every REST and SSE request must include `Authorization: Bearer <token>`. Token is generated on first run and printed to stdout/journald once.

No TLS enforcement in v0.1 (LAN). Users wanting WAN access are expected to front NOCS with a reverse proxy + TLS; this is out of v0.1 scope but not blocked.

### 7.2 Multi-client semantics (v0.1)

**Cooperative free-for-all.** Any request with the valid token can issue any command. No controller role, no lock, no handoff ceremony. Appropriate for a solo user with multiple devices.

Every command is logged in the session history with the connecting client's IP and user-agent, so the user can retrospectively see "my phone sent this command at 02:14."

### 7.3 Reserved API shape for persona B

To make the persona B migration additive:

- All command endpoints accept an optional `X-NOCS-Controller-Token: <lease-id>` header. In v0.1 it's ignored. In persona B, presence + match against the held lease becomes mandatory.
- E-stop endpoint will remain open to any authenticated identity, regardless of controller lease.
- Event SSE stream includes a `controller_changed` topic that's silent in v0.1.

## 8. Transport layer

### 8.1 Protocols

- **REST** (JSON) for all commands, queries, CRUD.
- **SSE** for server → client event streams. Single multiplexed stream per client at `/api/events?topics=mount,camera,safety,...`. Topic filtering via query param. Auto-reconnect handled natively by `EventSource`.
- **HTTP GET** for binary payloads: FITS downloads, thumbnail JPEGs, logs.
- **No gRPC** in v0.1. The PRD's "gRPC for permanent client communication" is reinterpreted as SSE. A future bidirectional-streaming need (most likely from persona B tooling) may revisit this surgically.

### 8.2 REST API shape (sketch, not exhaustive)

```
GET    /api/config                  # read global config
PATCH  /api/config                  # update config

GET    /api/devices                 # list connected devices + state
POST   /api/devices/{id}/connect
POST   /api/devices/{id}/disconnect
POST   /api/mounts/{id}/slew        # body: { ra, dec } or { target_id }
POST   /api/mounts/{id}/park
POST   /api/mounts/{id}/sync        # typically called by plate-solver service
POST   /api/cameras/{id}/expose     # body: { duration, filter, ... }
POST   /api/cameras/{id}/cool       # body: { setpoint }
POST   /api/filterwheels/{id}/select # body: { slot }
POST   /api/focusers/{id}/move      # body: { position } or { offset }
POST   /api/focusers/{id}/autofocus

GET    /api/targets/search?q=M31    # catalog lookup
GET    /api/targets/{id}            # full details incl. altitude, transit

POST   /api/sequences               # create + start a sequence
GET    /api/sequences/{id}          # poll status (or use events)
POST   /api/sequences/{id}/pause
POST   /api/sequences/{id}/abort

POST   /api/safety/e-stop
GET    /api/safety/rules            # current loaded rules
POST   /api/safety/rules/reload     # re-read safety.yaml

GET    /api/sessions                # list past sessions
GET    /api/sessions/{id}           # full session history + log
GET    /api/images/{id}.fits        # FITS download
GET    /api/images/{id}/thumb.jpg   # server-stretched preview

GET    /api/events?topics=...       # SSE
```

### 8.3 Event taxonomy (initial topics)

`mount`, `camera`, `filterwheel`, `focuser`, `sequence`, `safety`, `session`, `device_connection`, `system`.

Events are typed JSON with a `type`, `topic`, `ts`, and payload. Clients opt into topics via the query param.

## 9. Target picking & catalogs

### 9.1 v0.1 scope

Text-search target picker — no sky chart — against a bundled offline catalog. Selecting a target shows computed RA/Dec (epoch J2000 and current), current altitude, azimuth, airmass, and time to transit, given the configured observatory location.

### 9.2 Bundled catalogs

- **Messier** (110 objects)
- **Caldwell** (109 objects)
- **NGC + IC** (~13 000 objects)
- **Named stars** (~300)
- **Solar System** via ephemeris library (Sun, Moon, 8 planets, Pluto, optionally major moons)

Total bundled footprint target: under 10 MB.

No Tycho/Gaia full-sky star catalog in v0.1 (would only be needed for a chart).

### 9.3 Name resolution

1. Local catalog lookup first (fast, offline).
2. If not found and `online_resolver: true` in config, fall back to SIMBAD (VizieR as secondary).
3. Never silently slew on a resolver miss — return a search error to the user.

### 9.4 Coordinate math

Handled by the TargetService. Library choice deferred to implementation; requirements:
- Accurate Sun/Moon/planets ephemeris for a given time and location.
- Precession/nutation/aberration corrections from J2000 to JNow.
- Atmospheric-refraction-aware altitude calculation for transit/rise/set.

## 10. Imaging workflow (v0.1 MVP)

The ImagingService owns the sequence engine.

### 10.1 Sequence definition (JSON)

```jsonc
{
  "target_id": "messier:M31",
  "dither": { "enabled": true, "pixels": 10, "every_n_subs": 1 },
  "steps": [
    { "filter": "L", "exposure_s": 120, "count": 30 },
    { "filter": "R", "exposure_s": 180, "count": 10 },
    { "filter": "G", "exposure_s": 180, "count": 10 },
    { "filter": "B", "exposure_s": 180, "count": 10 }
  ],
  "pre_steps": [
    { "type": "slew_and_sync" },    // slew, plate-solve, sync, recenter
    { "type": "autofocus" }
  ]
}
```

### 10.2 Engine behavior

1. Run `pre_steps` in order.
2. For each step: select filter, loop `count` times: expose, download, save, optionally dither (offset mount by N pixels), repeat.
3. Between filter changes, optionally re-run autofocus (v0.2 feature flag; v0.1 does autofocus once at pre-step time only).
4. Any abort / pause / e-stop / rule trigger interrupts cleanly at the next safe boundary.

### 10.3 Dithering implementation note

Dithering in v0.1 moves the mount by a small pixel-count offset and waits a settle-time. No guiding feedback loop. This works for short-to-medium subs, which is the v0.1 target.

## 11. Plate solving

- **v0.1 default:** ASTAP, invoked as a local binary with its star DB.
- **Interface:** `PlateSolvingService` exposes `solve(fits) → {ra, dec, rotation, scale, solved_at} | failure`.
- **Pluggable:** `astrometry.net` local install can be added later by implementing the same interface.
- ASTAP binary and star DB are **not** bundled inside the NOCS JAR (license hygiene + JAR size). Instead:
  - Linux `.deb` packages declare ASTAP as a package dependency where available, or ship a small `nocs-astap-installer` helper that fetches ASTAP + its H18 star DB into `data_dir/astap/` on first run.
  - Windows installer runs a post-install step to fetch ASTAP + star DB.
  - The user can override the ASTAP binary path and star DB path in `config.yaml`.

## 12. Persistence

### 12.1 SQLite (schema outline, not final)

- `config_kv` — global key/value settings
- `observatories` — location, elevation, timezone, horizon mask
- `optical_trains` — named combinations of camera + filter wheel + focuser
- `device_profiles` — saved device configs
- `targets_custom` — user-added targets beyond the bundled catalog
- `sessions` — one row per observing session
- `session_events` — append-only event log per session
- `images` — metadata for saved FITS files
- `sequences` — sequence definitions and runs

Migrations via Flyway. Embedded catalogs are shipped as read-only SQLite tables or as data files loaded into memory on startup (implementation choice; user-visible API same either way).

### 12.2 Files on disk

Images live under a configurable `data_dir`, default `$XDG_DATA_HOME/nocs/` (Linux) or the equivalent Windows path.

```
data_dir/
├── sessions/
│   └── 2026-04-21/
│       └── M31/
│           ├── L_120s_001.fits
│           ├── L_120s_001.thumb.jpg
│           └── ...
├── logs/
│   ├── system.log           # SLF4J JSON output
│   └── session-2026-04-21.log   # human-readable session log
└── nocs.sqlite
```

Filename convention: `<filter>_<exposure>s_<nnn>.fits` where `<nnn>` is a zero-padded index within the step. Thumbnails stored alongside.

## 13. Services (v0.1 inventory)

- **ConfigurationService** — global config, observatories, optical trains, device sets.
- **LocationService** — server/client location detection; manage mount location (get/set).
- **DeviceService** — owns INDI client adapter and the abstract device instances; lifecycle + state machines.
- **ImagingService** — sequence engine (see §10).
- **TargetService** — catalog + name resolver + coordinate transforms (see §9).
- **PlateSolvingService** — ASTAP wrapper (see §11).
- **SafetyService** — rule engine + e-stop (see §6).
- **SessionService** — group work into sessions; write to `session_events` and the human session log.
- **ImageStoreService** — write FITS, generate thumbnails, index metadata.

Out of v0.1 but **architecturally reserved**:
- **GuidingService** — v0.2 (PHD2 integration first, native later).
- **SchedulerService** — v0.2+.
- **CalibrationService** — v0.2+.
- **WeatherService** — stubbed: receives events from a sensor driver if present; safety rules reference it.

Services communicate via the in-process Reactor event bus for pub/sub and direct method calls where appropriate. No microservice split.

## 14. Deployment & packaging

### 14.1 Artifacts

- **Linux arm64 `.deb`** for Raspberry Pi OS (RPi 4/5) — includes bundled JRE via `jpackage`.
- **Linux x86_64 `.deb`** for desktop Linux.
- **Windows installer** (`.msi` via `jpackage`).
- **Portable fat JAR** for advanced users, requires JRE 25.

Raspberry Pi is the demanding target: installer size, startup time, and memory must be acceptable there.

### 14.2 Runtime

- Systemd unit on Linux: `nocs.service`, enabled by the `.deb`, user-level.
- NOCS launches `indiserver` as a child process with the configured driver set.
- Logs: SLF4J + Logback → JSON to `data_dir/logs/system.log` + journald.
- Human-readable session log: a separate writer the SessionService owns, plain text, one line per significant event. Users actually read this one.

### 14.3 Startup

1. Load `config.yaml` (creates default on first run, prints generated token).
2. Open SQLite + run Flyway migrations.
3. Start HTTP server.
4. Start `indiserver` child.
5. Load `safety.yaml` if present; SafetyService starts monitoring.
6. Ready.

## 15. Web client

- **Stack:** React + Vite + TypeScript, served as static assets by the Spring app from the same origin.
- **Event consumption:** `EventSource` on `/api/events` with topic filtering.
- **Views (v0.1):**
  - Connect / hardware dashboard (device states, connect/disconnect)
  - Target search + details
  - Slew / plate-solve / sync controls
  - Autofocus panel
  - Sequence editor + runner (live progress)
  - Image gallery (thumbnails + on-demand FITS download)
  - Session history
  - Safety panel (loaded rules, e-stop button, trigger log)
  - Settings (config, observatory, optical trains)
- **FITS preview:** server generates stretched JPEG thumbnails on image arrival; full FITS downloads are on-demand. No client-side FITS rendering in v0.1.

## 16. Observability (v0.1)

- System log: SLF4J/Logback → JSON → file + journald.
- Session log: human-readable, one event per line, per-session file.
- Session history: structured rows in `session_events` with timestamps, caller identity, event type, payload — queryable via `/api/sessions/{id}`.
- No Prometheus, no OpenTelemetry, no tracing in v0.1. Persona B is the right time to introduce them.

## 17. Testing strategy

- Unit tests for services.
- **Simulator-based integration tests** against the INDI simulator drivers in CI — always green or the build fails. This is how we keep the software honest without hardware.
- One real-hardware test rig verified manually before releases (combo: one ZWO camera + one EQ-mount + one EFW + one EAF, or equivalent).
- Contract tests on the REST API.
- A smoke test that runs a tiny simulated sequence end-to-end from CLI.

## 18. Deferred / open questions

These are not blockers for starting the implementation plan but will need answers soon:

1. **Exact INDI client library / implementation approach** — adopt an existing open-source Java INDI client, or write a minimal one in-house.
2. **Ephemeris library choice** — pure Java option vs. JNI to `swisseph`/`libnova`. Affects RPi packaging.
3. **FITS stretch algorithm for thumbnails** — simple asinh vs. MAD-based percentile. Low stakes, pick during implementation.
4. **Session identity and time boundaries** — does a session auto-close at sunrise, on disconnect, on user action? Proposal: manual open/close with auto-close-on-sunrise as a fallback; decide during ImagingService implementation.
5. **Atomicity of E-stop** — if parking fails mid-e-stop, what's the recovery state? Proposal: E-stop transitions all applicable devices to an `e_stopped` state that blocks further commands until manually reset from the UI.
6. **Target altitude limit source** — horizon mask is per-observatory, altitude-limit rule should reference it. Schema needs `horizon_mask` on `observatories`.
