# NOCS — Roadmap to v1.0

Status: draft, started · Last updated: 2026-11-04 · Previous: [v0.1](v0.1.md)

v0.1 proves the idea on one rig: a freshly flashed Pi 5 runs a whole night from a
phone, on the maintainer's ZWO equipment. **v1.0 is the first version recommended
to other people**: usable by someone who is not the maintainer, on a rig that is
not the lab's, night after night, updated without losing anything.

This document starts describing it. Nothing here is decided yet: themes are
candidates, phases and estimates come once v0.1 ships and its field test's
findings are known. Planning assumptions stay those of [v0.1](v0.1.md) (one
developer, 5–10 hours a week).

## What v1.0 promises

- **Compatibility.** From 1.0.0 on, a change that is not backward compatible needs
  a major release (2.0). Before v1.0 nothing is kept compatible: profiles,
  settings, state, the API and files on disk change freely.
- **Updates that keep the data.** Profiles, settings, sequences, the calibration
  library and the frame catalog survive every 1.x update, migrated when their
  format changes.
- **A night that does not depend on the maintainer.** The user guide, the app's
  own messages and the diagnostics bundle are enough to set up a rig, image and
  report a problem.

## Exit criterion (draft)

Someone other than the maintainer, with a rig of their own that is not all ZWO,
flashes the image, follows the [quick start](../user/quick-start.md) and images
several nights over a few weeks, updating NOCS in between, without help, without
SSH and without losing a night to NOCS.

## Candidate themes

### Compatibility and updates

- A version on every format NOCS writes (profiles, settings, sequences, state on
  disk), with migrations run on start; the SQLite catalog already migrates
  (ADR 0013).
- Rollback across a migration: today a rollback reinstalls the previous package
  (ADR 0025), which cannot read data a newer version migrated.
- Export and import of the configuration (profiles, settings, sites), as a backup
  and to move to a new card.
- Decide what the promise covers: data on disk certainly; the API only if clients
  other than the bundled web app are to be supported.

### More hardware

- The mounts already owned: ZWO AM7, iOptron GEM45G (profiles and driver quirks,
  left after phase 2's exit).
- Canon DSLR through gphoto.
- Off-axis guider as a configuration of its own (phase 4 tested a guide scope
  first).
- Other power boxes and focusers that users report; a way to send a hardware
  report from the app.

### Robustness

- Crash recovery of a running sequence beyond a nocsd restart (ADR 0032 covers the
  restart).
- USB reset of a device that stops answering, after a driver restart and a power
  cycle (ADR 0030, ADR 0032).
- Longer soak tests than the 8 h simulated night ([spike](../spikes/pi5-soak.md)),
  and USB bandwidth with every device on the Pi 5 (design §16).

### Getting the images

- SMB share for desktop access to the frames (design §8).
- Resumable downloads of a night's zip (ADR 0013).

### Planning the night

- A horizon profile for visibility and polar alignment (ADR 0034).
- Save a preview after the fact: keep the FITS behind each camera's latest preview
  (phase 2, pending).
- Filter wheels: find which filter sits in each slot (e.g. from a flat's
  brightness per slot) instead of asking (ADR 0016).
- Mosaic planning.

### Calibration, the rest

- Flats as a sequence instruction (dawn flats at the end of a night), INDI light
  boxes, dark flats, a light-leak check on darks
  ([calibration plan](v0.1/calibration.md)).

### Access and security

- HTTPS on the LAN with a local certificate authority (~8–10 h): it brings
  geolocation, offline installation of the PWA and the screen's wake lock
  (ADR 0014, [phase 6](v0.1/phase-6.md)).
- Remote access outside the LAN, relay or VPN-style, with the same protocol
  (design §13): in or out of v1.0 is an open question.

### Project

- Every ADR accepted, [design](../design.md) and [ux](../ux.md) out of draft.
- The user guide complete for what v1.0 ships, translated (en/es) like the app.
- Contributing guide, issue templates for bugs and hardware reports.

## Not in v1.0 (proposal)

The design's non-goals stay out: EAA and live stacking, observatory automation
(roofs, domes, weather safety), ASCOM Alpaca and INDIGO adapters, several rigs on
one server, planetary imaging (design §1, §13).
Live stacking is nevertheless being built apart from v1.0, behind a switch that is
off by default: [live-stacking.md](live-stacking.md), ADR 0039.

## Open questions

- Which rigs, besides the lab's, must v1.0 be tried on, and who tries them?
- Is the API part of the compatibility promise, or only data on disk?
- Is a PC install as supported as the Pi image, or a second-class path?
- Remote access and HTTPS on the LAN: in v1.0 or after?
- How many v0.x releases on the way, and what each one brings.
